# pathguard

パスに触れてよいかの判定を 1 つに —— [nlink-jp](https://github.com/nlink-jp) のツール向け。

標準ライブラリだけで書いた Go のライブラリ。パスが、何も届いてはならない場所 —— システムのフォルダ、
資格情報の置き場所、エージェントの設定、サーバー自身のディレクトリ —— の中にあるかを判定する。判定は
**名前だけでなくファイルの実体でも**行うので、大文字小文字を区別しないディスクでの綴り違い、シンボリック
リンク、ファームリンクで通り抜けることはできない —— その場所がまだ存在しなくても。

## パッケージ

| パッケージ | 中身 |
|---------|------------|
| `pathguard` | 汎用の判定。パスをリンク 1 段ずつ解決し、場所と実体・名前の両方で比べる。場所の一覧を 1 つ持ち、2 つのファイルの方針（Local と Outbound）を作る。MCP のことは知らない。 |
| `pathguard/workdir` | 組織 ADR-021（ファイルを受け渡す MCP サーバーの作業ディレクトリの契約）を `pathguard` の上に実装したもの。ツールの引数か `_meta` からの `work_dir`、閉じた検査の一覧、エラーコード。 |

## インストール

```bash
go get github.com/nlink-jp/pathguard
```

## 使い方

### サーバーが呼び出し側の作業ディレクトリを検査する

```go
import (
    "github.com/nlink-jp/pathguard"
    "github.com/nlink-jp/pathguard/workdir"
)

r := workdir.NewResolver(workdir.Options{
    Protected:    []pathguard.Place{pathguard.ServerDir(configDir, "")},
    RequiredHint: "Results come back as paths, and a path you cannot open is worth nothing.",
})

dir, err := r.Resolve(args.WorkDir, requestMeta) // 引数、無ければ _meta["jp.nlink/work_dir"]
var e *workdir.Error
if errors.As(err, &e) {
    // e.Code は work_dir_required / _invalid / _not_found / _not_writable / _denied
    // work_dir_denied の e.Details: {"work_dir", "resolved", "reason"}
}
```

ゼロ値の `workdir.Resolver` はすべてを拒む —— 働くものを作るのは `NewResolver` だけ。ホームディレクトリが
分からないとき、または守る場所に絶対パスが無いとき（`ServerDir("")`）は、すべての呼び出しを理由を添えて拒む。

`Options.Home` が空なら、床は環境が示すホーム（`$HOME`）について作り、それと違うときはユーザー
データベースにあるアカウント自身のホームについても作る。`HOME` をほかへ向けて起動したサーバーでも、
本物の `~/.ssh` は守られる。

### 呼び出しが実際に使うディレクトリ

ワークスペースは作業ディレクトリの下のディレクトリ `<work_dir>/<workspace_id>` で、`work_dir` の検査だけでは
覆えない。`work_dir=~/.config` と `workspace_id=gh` は `~/.config/gh` になる。作る前、使う前に確かめる ——
まだ存在しなくてよい:

```go
if err := r.CheckBeneath(filepath.Join(dir, workspaceID)); err != nil {
    // *workdir.Error、work_dir_denied、details {"path", "reason"}
}
```

### 呼び出しが名指すファイル

```go
// このマシンの上で読み書きする:
if reason, why := r.LocalPath(raw, resolved); why != "" { /* reason を添えて拒む */ }

// マシンの外へ送る（アップロード）:
if reason, why := r.OutboundPath(raw, resolved); why != "" { /* 拒む */ }
```

パスは、ファイルがあるかを問う前に、行き着く場所で判定する（答えがどのファイルが存在するかを教えないように）。
`pathguard.Where` がその行き着く先を返す —— リンクはすべて、行き先の無いものも行き先までたどり、存在するパスなら
`filepath.EvalSymlinks` と同じ。`Forms` の末尾をその代わりにしないこと: 形は重複を除くので、リンクの連鎖が既に出た
綴りに戻ると、行き着く先は前の方の形になる。

```go
where, ok := pathguard.Where(raw)
if !ok { /* リンクの連鎖が終わらない: 拒む */ }
if reason, why := r.LocalPath(raw, where); why != "" { /* 拒む */ }
// ここで初めて: 存在するか、通常ファイルか、……
```

`Resolver` を持たない呼び出し箇所は、パッケージの関数を使う。方針は、`Options.Home` が空のときと同じく
このプロセスのホームディレクトリから作る（ホームが分からなければ拒む）:

```go
if why := workdir.Sensitive(raw, resolved); why != "" { /* 拒む */ }         // Local
if why := workdir.SensitiveOutbound(raw, resolved); why != "" { /* 拒む */ } // Outbound
```

## 2 つのファイルの方針

| | Local（ここで読み書き） | Outbound（マシンの外へ送る） |
|---|---|---|
| **あなたの**ホームにある本物の資格情報・エージェント制御の場所（`~/.ssh`、`~/.aws`、`~/.kube`、`~/.config/gh`、`~/.netrc`、`~/.bash_history` など） | 拒む | 拒む |
| どこにあっても `.env` / `.env.*`（`.env.example`・`.sample`・`.template`・`.dist` を除く） | 拒む | 拒む |
| ほかの場所にある同じ名前のもの —— `evidence/home/bob/.bash_history`、プロジェクトの `.npmrc` | 通す | 拒む |
| どこにあっても秘密の名前 —— `id_rsa`、`credentials.json`、`*service-account*.json` | 通す | 拒む |
| サーバーが守るディレクトリ | 拒む | 拒む |

インシデント対応で集めた証拠の中の資格情報ファイルの写しは、分析する人が読む必要のあるものである。一方、
マシンの外へ出た鍵は取り返せない。システムのフォルダは作業ディレクトリを拒むもので、ファイルは拒まない。

## パスの比べ方

- **リンクの各段が「形」になる。** リンクは 1 段ずつ解決する。渡されたままのパス、途中のすべてのパス、
  最後のパスをすべて調べる。`~/.ssh/config` 自体が同期フォルダへのリンクのとき、`work/x → ~/.ssh/config`
  と仕込んだリンクは、途中の形が `~/.ssh` の中にあるので拒まれる。
- **実体と名前、常に両方。**
  - 実体の比較では、各場所を、そのパスのうち存在するいちばん深いところ —— 場所そのもの、または場所が
    作られるはずのディレクトリ —— と、その下に続く名前とで固定する。形の側の存在する上位のどれかが同じ
    ファイル（`os.SameFile`）で、その下に続く名前が場所の名前で始まれば一致とする。これで、存在する部分の
    あらゆる綴り —— 大文字小文字、リンク、ファームリンク、`/.nofollow`、`/.vol`、Unicode の正規化、
    `~/.netrc` のようなファイルへのハードリンク —— を捕まえる。`~/.aws` がまだ無いうちの
    `~/.aws/credentials` も同じように捕まえる。
  - 名前の比較は、実体の番号を信用できないファイルシステムでも守りになる。
- **名前はディスクと同じやり方で同一視する。** APFS は名前を ASCII の小文字化ではなく Unicode のケース
  フォールディングで照合する。`id_rſa` で `id_rsa` が開き、ケルビン記号で `k` が、`.ﬆ` で `.st` が開く。
  名前の比較も同じやり方で同一視し、`ß` → `ss` やラテン文字の合字の展開も含める。APFS が守る名前の文字と
  同じとみなす文字はすべて同一視する。正規化（`é` の合成形と分解形）は同一視せず、実体の比較が受け持つ。
- **資格情報のディレクトリの中のリンクの行き先も守る。** `~/.ssh/config` が同期フォルダへのリンクなら、
  その指す先のファイルをそちらの名前で渡しても拒み、まだ無いならそこに作ることも拒む。そのディレクトリ
  自身やその上（`/`、ホーム）を指すリンクは、リンク自身の位置だけを守る。そうしないとすべてを拒んでしまう。
  サーバー自身のディレクトリの中のリンクはたどらない。作業ディレクトリを指していることがあるため。
- **NUL バイトを含むパスは拒む**（`unresolvable_path`）。どのシステムも開けないが、C に渡したパスは NUL で
  終わる。`.netrc\x00.safetensors` は、ある文字列として判定され、別の文字列として開かれてしまう。
- **その場所そのものだけの項目は、そのものとだけ比べる。** `/`、`/private/var`、ホームは、それ*自体*である
  作業ディレクトリを拒み、その下すべては拒まない。
- **どのシステムも開けない長さのパスは拒む**（`unresolvable_path`）: 4096 バイト、Windows では 32 KiB を
  超えるもの。この上限は、リンクをたどって長くなった形も含め、すべての形にかかる。これで、パスの引数 1 つに
  かかる費用に上限がつく。現実的なパスでも許される最長のパスでも約 2 ms。最悪の場合 —— すべての形を上限まで
  伸ばすように 39 個のリンクを仕込んだ鎖 —— で約 0.3 秒。

## 限界

これは床であって境界ではない。

- **判定はその時点の写しである。** 検査してから開くまでの間に作られたリンクは見えない。検査に渡した解決済みの
  パスを開き、書き込みは `os.Root` か `O_NOFOLLOW` で閉じ込めること。この競合を閉じるのは、サーバー自身の
  封じ込めである。
- 資格情報のディレクトリの中のファイルや `.env` への別名のハードリンク、秘密の写しは、Local の方針では検出しない
  —— ディレクトリはそれ自身の実体で比べ、中のファイルでは比べない。床の場所そのものであるファイル（`~/.netrc`）への
  ハードリンクは実体の比較で捕まるが、それも存在するあいだだけ。
- 資格情報のディレクトリの項目を通って `..` で抜けるパス（`~/.ssh/ENTRY/../../Music/x`、またはその綴りを行き先に
  持つリンク）は、通った場所ではなく行き着く場所で判定する。そのため、`ENTRY` がリンクか・行き先がどこかが答えに
  出うる。
- `work_dir` の検証は組織 ADR-022 §4 の順序（見つからないが拒否より先）なので、資格情報のディレクトリを指す
  `work_dir` は、そのディレクトリがあるかどうかで答えが変わる。
- 非 ASCII のリンク先の名前を別の Unicode 正規化で綴ると、実体の比較で捕まるのはそれが存在するあいだだけ。
- 行き先までたどるのは、資格情報・エージェント制御のディレクトリの直下にあるリンクだけ。もっと深いところの
  リンク（`~/.ssh/keys/work → …`）は、リンク自身の位置は守られるが、行き先は守られない。大きなディレクトリを
  指すリンク（`~/.aws/x → ~/Dropbox`）は、その全体を守る。拒むときはリンクの名前を示す。
- 場所として守るのは、サーバーを動かしているアカウントのホームだけ。ほかのユーザーの `.claude`・`.gemini`・
  `.codex` は、どちらの方針でも普通のディレクトリとして扱う（gem-agent と lagent はどのホームでも名前で
  拒む）。ほかのユーザーの `.ssh`・`.aws` などは、Outbound の方針では引き続き名前で拒む。
- 実体の番号が不安定なファイルシステムでは、実体の比較が衝突して正当なパスを拒むことがある。
- まだ存在しない場所の名前は、存在するいちばん深いディレクトリより下の部分を、Unicode の正規化をせずに
  比べる。影響するのは、非 ASCII の名前を持ち、まだ作られていない守るディレクトリだけで、床の名前は
  すべて ASCII である。
- **Windows は推論であって実測ではない。** 扱いはプラットフォームの文書どおりの動作に従い、コンパイルは
  通り、名前の規則は単体テストしてあるが、Windows の上で動かしてはいない:
  - すべてのパスを、Windows 自身の正規化である `filepath.Abs` に通す;
  - 名前はストリームの接尾辞（`.env::$DATA`）と末尾の `.`・空白を除いて比べる;
  - ジャンクションはリンクとしてたどる;
  - ルートから始まるリンクの行き先（`\Users\u`）は、リンクと同じドライブにあるとする。

  8.3 形式の短い名前（`CREDEN~1.JSO`）は、存在する場所には実体の比較で届くが、Outbound の方針の名前だけの
  規則はすり抜ける。
- ホームが空か相対パスなら、分からないものとして扱い、すべてを拒む。
- `HOME` が別のディレクトリを指していても、アカウント自身のホームも守る（`user.Current` はユーザーデータベースを
  読み、darwin では `CGO_ENABLED=0` でも `HOME` を見ない）。そのため `HOME` を差し替えたテストでも、`-tags osusergo`
  を付けてビルドしない限り、本物の資格情報のディレクトリを読み取りで stat し、一覧する。
- 判定のたびに場所を用意し直す（資格情報のディレクトリの中のリンクを読む）ので、1 回に約 2.5 ms かかる。1 回の
  呼び出しで数百のパスを判定すれば、その数だけかかる。
